# CLAUDE.md

Инструкции для разработки self-hosted CI/CD-хаба с метриками (рабочее название — **Ranger**, поменять на своё в разделе 1, если решишь иначе).

---

## 1. Что это за проект

Лёгкая self-hosted альтернатива Jenkins + Portainer + кусок Grafana в одном инструменте, для одного сервера и 2–5 доверенных пользователей. Не публичный сервис, не мультитенантный PaaS — личный инструмент, который быстро настраивается и не требует поднимать три разных сервиса ради одного домашнего сервера.

Сценарий использования целиком: добавил проект по SSH-ссылке на git-репозиторий → задал команды install/test/build → нажал «собрать» или настроил cron → следишь за сборкой в реальном времени в одной вкладке (лог, статус шагов, результаты тестов) → после деплоя смотришь метрики контейнера и хоста там же, без переключения между инструментами.

Из этого следуют приоритеты:

1. **Скорость настройки нового проекта важнее гибкости конфигурации.** Три текстовых поля команд и SSH-ссылка — это весь конфиг. Никакого YAML DSL, никакой плагинной системы шагов.
2. **Наблюдаемость (логи + метрики) — не довесок, а треть продукта.** Вкладка сборки без живого лога — это не MVP этого проекта, это недоделанный MVP.
3. **Терминал и файловый доступ — это функция для крайних случаев, а не витрина.** Проектируется последней и с отдельным контуром безопасности, не наравне с остальным UI.
4. **Проект дальше ведётся вручную, не агентом.** Это меняет то, как пишется код, не только то, что он делает — см. раздел 2.
5. **Исполнение кода в песочнице — переиспользуемый модуль, не внутренняя деталь build-пайплайна.** Тот же модуль будет использован в отдельном учебном проекте как «судья» для задач по алгоритмам — см. раздел 9. Проектировать его границу с самого начала, не выносить задним числом.

## 2. Как пишем код — проект читает и правит человек

Это не разовая генерация, после которой код никто не открывает. Через полгода в файл `builds.service.ts` полезешь ты сам, без контекста этого разговора в голове. Отсюда конкретные правила, не пожелания:

- **Абстракция появляется на второе применение, не раньше.** Если паттерн используется в одном месте — пиши его прямо там. Обобщать «на будущее» после первого же случая — код ради кода: он выглядит как забота о расширяемости, а на деле добавляет слой, который придётся понимать при каждом чтении, ради гибкости, которая может никогда не понадобиться.
- **Плоская структура сильнее глубокой иерархии.** Модуль NestJS = одна папка с `*.controller.ts`, `*.service.ts`, `*.module.ts`, DTO рядом же. Не разносить по `interfaces/`, `abstract/`, `base/`, если под этим нет второй реализации.
- **Без общих «фреймворков внутри фреймворка».** Не писать свой generic `BaseCrudService<T>` поверх Prisma/TypeORM ради шести сущностей — прямой код, повторяющийся в шести местах, читается быстрее, чем шаблон с дженериками, который нужно распаковывать в голове.
- **Комментарий объясняет «почему», не «что».** Если тянет прокомментировать «что» — значит, код сам должен быть понятнее (переименовать переменную, разбить функцию), а не обрасти комментарием.
- **Ошибки обрабатываются там, где с ними можно что-то сделать.** Не оборачивать каждый вызов в `try/catch` рефлекторно — только там, где есть осмысленное действие на ошибку (ретрай, откат, понятное сообщение пользователю). Остальное пусть падает и логируется на верхнем уровне (глобальный exception filter в Nest).
- **Один способ сделать типовую вещь, а не два-три на выбор.** Если для похожей задачи в одном месте использован `dockerode`, а в другом — сырой `exec('docker ...')`, это сигнал вернуться и унифицировать, а не оставить как есть.

Мысленная проверка перед тем, как закоммитить: «пойму ли я этот файл через полгода за две минуты, без памяти о том, зачем он так написан».

## 3. Стек

| Слой | Выбор | Замечания |
|---|---|---|
| Backend | NestJS + TypeScript | модули: projects, builds, deployments, containers, metrics, auth |
| Пакетный менеджер / рантайм | Bun | ставь зависимости и гоняй скрипты через Bun. NestJS в целом совместим, но декораторы и `reflect-metadata` — исторически чувствительное место для рантаймов помимо Node. В итерации 1 отдельным шагом проверь, что DI, гварды и WebSocket-gateway у Nest работают под Bun-рантаймом в проде, не только на дев-сервере. Если всплывут проблемы — Bun остаётся как пакетный менеджер и раннер скриптов, а сам процесс в проде поднимается на Node; это не откат, а нормальный компромисс |
| БД | PostgreSQL | Prisma или TypeORM — на усмотрение, не менять посреди проекта |
| Очередь сборок | BullMQ (Redis) или очередь на Postgres (`pg-boss`) | один воркер на проект — сборки одного проекта не идут параллельно |
| Docker-интеграция | `dockerode` (Docker API через сокет) | сокет монтируется только в backend-контейнер, никогда не пробрасывается в контейнеры сборки. Единственное исключение из «одного способа» — compose-деплой через CLI `docker compose`: compose — отдельная программа, в dockerode её нет |
| Реалтайм | WebSocket (Nest Gateways) | стриминг логов сборки, логов контейнеров, метрик |
| Frontend | React + TypeScript + Tailwind + Vite | тот же стек, что в остальных проектах — переиспользуй компоненты, где осмысленно |
| Состояние на клиенте | Zustand | сессии сборок, открытые вкладки логов, выбранная тема и язык |
| Локализация | `react-i18next` (или аналог) | RU и EN, ключи с самого начала, не хардкодить строки в JSX — см. раздел 6 |
| Git-операции | системный `git` через shell (SSH deploy-key) | не писать свой git-клиент, не поднимать свой git-сервер — репозиторий остаётся на GitHub/GitLab |
| Авторизация | сессии + cookie, пароли через `argon2` | без OAuth, без внешних провайдеров — не нужно на 2–5 пользователей |
| Хостинг | сам сервер, `docker compose` | хаб деплоит сам себя тем же способом, что и остальные проекты — хорошая проверка архитектуры |

Не добавлять Kubernetes, Nomad, Consul или что-либо оркестрационного уровня — это один хост, не кластер.

## 4. Модель данных (ядро)

```
users
  id, email, password_hash, role ('admin' | 'operator' | 'viewer'), must_change_password, created_at

projects
  id, name, git_url, branch, owner_id
  install_cmd, test_cmd, build_cmd        -- обычные shell-команды, не DSL
  trigger_mode ('cron' | 'manual'), cron_expr (nullable)
  is_public                               -- показывать ли на публичной странице статуса
  deploy_mode ('container' | 'compose'), compose_file  -- compose включает только admin (раздел 7)
  env_keys, encrypted_env                  -- переменные окружения для сборки и деплоя: имена открыто,
                                           -- значения одним зашифрованным JSON, в API не возвращаются
  deploy_key_id -> deploy_keys.id

deploy_keys
  id, project_id, encrypted_private_key   -- шифруется на уровне приложения, права файла 600 если хранится на диске
                                           -- НИКОГДА не логируется, не возвращается в API-ответах целиком

builds
  id, project_id, status ('queued'|'running'|'success'|'failed'|'rolled_back')
  branch                                   -- ветка этого запуска; может отличаться от projects.branch
  triggered_by ('cron'|'user_id'), started_at, finished_at
  steps: jsonb [{ name: 'install'|'test'|'build'|'deploy', status, duration_ms, log_ref }]

test_results
  id, build_id, passed (bool), output (text)

deployments
  id, project_id, build_id, container_id, status, deployed_at, rolled_back (bool)

audit_log
  id, user_id, action, target, created_at   -- обязателен с появлением терминала (фаза 2)
```

Секреты (`deploy_keys`, `projects.encrypted_env`, любые токены) — единственная таблица в проекте, где сокращать путь недопустимо: шифрование на уровне приложения (не полагаться только на шифрование диска), исключение поля из любых `SELECT *` в API-слое, отдельный аудит на чтение (кто и когда запрашивал расшифровку).

## 5. Итерации

Работаем по порядку, следующая не начинается, пока текущая не закрыта по разделу 8.

### Итерация 1 — ядро: проект → сборка → лог
- CRUD проектов (SSH URL, ветка, deploy-key, три команды, режим триггера)
- Ручной запуск сборки, очередь на один воркер на проект
- Контейнер сборки: клонирование по SSH, `install` → `test` → `build`, с таймаутом и лимитом ресурсов (`--memory`, `--cpus`)
- Модуль исполнения кода в песочнице вынесен отдельно с узким интерфейсом (см. раздел 9) — build-пайплайн вызывает его как библиотеку, не наоборот
- Вкладка сборки: статус по шагам, живой лог по WebSocket, результат тестов
- Авторизация: 2–5 пользователей, сессии, без ролей пока (роль появится в итерации 4)
- Проверка совместимости NestJS-рантайма с Bun в проде (см. раздел 3) — сделать до того, как на этом рантайме построено всё остальное
- Хаб задеплоен и реально собирает хотя бы один настоящий проект к концу итерации

### Итерация 2 — деплой и контейнеры
- Шаг деплоя: остановка старого контейнера → запуск нового → health-check → откат при неудаче
- Список запущенных контейнеров (не только своих, все на хосте): статус, живые логи по WebSocket
- Cron-триггер сборки как альтернатива ручному
- Файловый браузер: только чтение, только рабочие директории проектов и их volume'ы — не весь диск хоста

### Итерация 3 — метрики
- Метрики хоста: CPU, RAM, диск, обновление раз в несколько секунд
- Метрики по каждому контейнеру: CPU, RAM, график за последний час (`docker stats`, не Prometheus)
- Вкладка метрик встроена в общий вид проекта, не отдельным неочевидным разделом

### Итерация 4 — роли, аудит, терминал
- Роль `admin` vs `operator`: только admin видит терминал и может расшифровывать deploy-key
- Терминал: вход в шелл конкретного контейнера/рабочей директории проекта, НЕ в хост-шелл напрямую; отдельная повторная аутентификация перед входом
- Журнал аудита: кто зашёл в терминал, кто нажал деплой, кто запросил секрет — видно в UI, не только в БД
- Откат на произвольную предыдущую успешную сборку из истории (не только автоматический откат при неудачном health-check)

### Итерация 5 — ветки, страница статуса, пользователи
- Ручной выбор ветки для конкретного запуска. Сборка не с основной ветки проекта проходит install/test/build, но шаг деплоя пропускается — работающая версия не подменяется экспериментальной веткой
- Публичная read-only страница статуса: только проекты с включённым флагом «публичный», только название, статус и время последней сборки — без логов, URL репозитория и веток
- Три фиксированные роли: `admin` — всё, включая пользователей, терминал и расшифровку deploy-key; `operator` — сборки, деплой, откат, редактирование проектов; `viewer` — только просмотр
- Регистрации нет, SMTP-доступ по email удалён. Первый admin создаётся при старте на пустой базе с email из `ADMIN_EMAIL`, сгенерированный пароль (16 hex-символов) один раз печатается в лог контейнера. Потерянный пароль сбрасывается командой внутри контейнера
- Админка пользователей: admin видит всех, создаёт (пароль генерируется, показывается один раз, при первом входе обязателен к смене), меняет роль, сбрасывает пароль, отключает и включает. Не удаляет: записи журнала аудита ссылаются на пользователя, история должна переживать уход человека. Себя отключить или понизить нельзя — иначе можно остаться без admin'а

### Итерация 6 — переменные окружения и compose-деплой
- Переменные окружения проекта: шифруются как deploy-key, попадают в шаги сборки и в задеплоенный контейнер, значения не возвращаются в API, длинные маскируются в логе сборки
- Второй режим деплоя — `docker compose up` по файлу из репозитория, для проектов из нескольких сервисов. Включает и меняет только admin (с аудитом); репозиторий и ветку compose-проекта меняет только admin
- Отката для compose-деплоя в первой версии нет: при неудаче сервисы остаются как есть. Откат — следующий этап (нужно хранить образы сервисов по сборкам)

### Не делаем (решено)
- Уведомления в Telegram
- Консоль хоста: терминал остаётся только в контейнере или рабочей директории проекта (раздел 7)

## 6. Дизайн — operator console, не витрина

Это инструмент, которым пользуются каждый день, а не портфолио-лендинг — амбиентная 3D-сцена и медленные анимации здесь неуместны, приоритет — плотность информации, скорость и однозначность, без визуального шума.

**Темы.** Две полноценные темы, светлая и тёмная, обе — не «дефолт и заглушка». Токены цвета определяются переменными (CSS custom properties) один раз, компоненты никогда не хардкодят hex — иначе вторая тема неизбежно разъедется с первой при любом будущем изменении. Переключатель темы — в шапке, выбор сохраняется в `localStorage`, по умолчанию берётся `prefers-color-scheme` при первом заходе.

**Локализация.** RU и EN с самого начала, не поверх готового UI задним числом — переносить хардкоженные строки в словарь после того, как интерфейс написан, дороже, чем сразу писать через `t('builds.status.failed')`. Переключатель языка рядом с темой, выбор в `localStorage`. Форматы дат/чисел идут через `Intl`, не через ручную конкатенацию строк.

**Не перегруженный интерфейс** — конкретные правила, не общие слова:
- На экране одновременно — то, что нужно для текущего действия, а не всё, что вообще есть в системе. Расширенные настройки проекта (нечастые поля) сворачиваются, а не стоят открытыми по умолчанию.
- Один акцентный цвет на весь интерфейс, не палитра «на каждый случай». Статус кодируется цветом **и** иконкой/текстом одновременно (зелёный/жёлтый/красный сами по себе недостаточны, особенно с учётом двух тем).
- Моноширинный шрифт — только для того, что машинно-точное: статусы, ID сборок, время выполнения, ветка, хеш коммита. Обычный текст — обычным шрифтом, не всё подряд в моноширинном ради «технического» вида.
- Layout: боковая панель со списком проектов, основная область — вкладки Overview / Builds / Logs / Metrics / Console (Console — только для admin, появляется в итерации 4).
- Логи и метрики — сворачиваемые панели, не модальные окна поверх всего экрана.
- Командная палитра `Cmd+K` для перехода между проектами и запуска сборки — здесь она оправдана сильнее, чем на портфолио, потому что инструмент используется руками каждый день.
- Никаких decorative-анимаций на появление панелей — статус обновляется мгновенно, без fade-in.

## 7. Безопасность — не раздел «на будущее», проверяется в каждой итерации

- Docker-сокет доступен только backend-процессу, никогда не пробрасывается внутрь контейнера сборки или деплоя одним контейнером. Исключение — compose-деплой: compose-файл из репозитория сам решает, что монтировать (включая сокет и пути хоста), то есть равен root на сервере. Поэтому режим включает только admin, с записью в аудит, и только admin меняет репозиторий и ветку такого проекта. Окружение самого Ranger (секреты) в `docker compose` не передаётся — только переменные проекта.
- Сборка выполняется без `--privileged`, без сети наружу сверх необходимого, с жёсткими лимитами CPU/памяти/PID и обязательным таймаутом.
- SSH deploy-key — read-only на стороне git-провайдера (GitHub позволяет выдать deploy-key только на чтение), хранится зашифрованной, не появляется в логах сборки ни при каких обстоятельствах (проверить, что shell-команды не печатают её при ошибке).
- Любой эндпоинт, доступный из интернета (если хаб не строго на localhost/VPN), защищён минимум паролем; сборочные вебхуки, если появятся, — HMAC-подписью.
- Терминал (итерация 4) — отдельная аутентификация, обязательный лог сессии, доступ только у роли `admin`.

## 8. Готовность итерации

1. Проверка типов, линт и сборка (backend и frontend) проходят без ошибок под выбранным рантаймом (Bun, с учётом оговорки в разделе 3).
2. Хаб реально задеплоен на сервере и используется хотя бы для одного настоящего проекта — не только для демо-репозитория.
3. Секреты (deploy-key) не появляются ни в одном логе, ни в одном сетевом ответе целиком — проверено вручную.
4. Сборка с истёкшим таймаутом или превышением лимита ресурсов корректно останавливается и помечается failed, а не висит.
5. При падении сборки/деплоя причина видна в UI без захода в базу или в docker logs руками.
6. Обе темы дают достаточный контраст текста, ни один hex-цвет не захардкожен в компоненте.
7. В интерфейсе нет строк, не проходящих через словарь локализации — переключение RU/EN не оставляет смешанного языка на экране.

## 9. Общий исполнитель кода (sandbox executor) — переиспользуется вне Ranger

Этот модуль запускает произвольный код в изолированном контейнере с лимитами и таймаутом и возвращает результат. Ranger использует его для шага сборки (`install`/`test`/`build`). Отдельный проект — учебная платформа с задачами по алгоритмам (JS/TS) — будет использовать его как «судью», прогоняющего решение задачи против скрытых тестов. Это одна и та же операция с разным содержимым на входе, поэтому она живёт как самостоятельный пакет, а не как код внутри `builds.service.ts`.

**Форма пакета, не сервиса.** На одном self-hosted сервере для личного использования отдельный сетевой микросервис ради этого — лишняя точка отказа и лишний деплой. Модуль оформляется как обычный npm/workspace-пакет (например, `@ranger/sandbox-executor` или нейтральное имя без привязки к Ranger в названии, раз он используется и вне его), оба проекта подключают его как зависимость и запускают в своём процессе. Превращать в отдельный сервис — только если проекты реально разъедутся на разные хосты, не раньше.

**Интерфейс — узкий, без знания о домене вызывающего:**

```ts
interface ExecuteOptions {
  image: string;            // образ с рантаймом, для v1 — только Node/Bun
  command: string;          // команда запуска внутри контейнера
  stdin?: string;           // вход, если задача его ожидает
  timeoutMs: number;
  memoryLimitMb: number;
  cpuLimit: number;
  workdir?: string;         // смонтированная рабочая директория (для Ranger — репозиторий, для судьи — временный файл с решением)
  env?: Record<string, string>; // переменные окружения процесса (для Ranger — env проекта)
}

interface ExecuteResult {
  stdout: string;
  stderr: string;
  exitCode: number | null;  // null — если убито по таймауту
  durationMs: number;
  timedOut: boolean;
}

function execute(options: ExecuteOptions): Promise<ExecuteResult>;
```

Модуль ничего не знает про `project`, `build`, `lesson` или `exercise` — эти сущности остаются в вызывающем проекте. Это то, что делает переиспользование настоящим, а не поверхностным: если модуль потянет за собой хоть одно понятие из домена Ranger, учебной платформе придётся либо тащить это понятие к себе бессмысленно, либо форкать модуль — и тогда переиспользования не будет.

**V1 — только один рантайм (Node/Bun).** Поддержку других языков (если когда-нибудь понадобится Python для чего-то ещё) добавлять по факту необходимости, не заранее — то же правило «абстракция на второе применение», применённое теперь и к языкам исполнения.

**Безопасность этого модуля отдельно от специфики Ranger:** без `--privileged`, без сети наружу по умолчанию, жёсткие лимиты CPU/памяти/PID, обязательный таймаут с принудительным `SIGKILL` по истечении. Это применимо к обоим потребителям одинаково — учебная платформа исполняет код студента (тебя), которому доверяешь не больше, чем содержимому чужого репозитория в Ranger.По
