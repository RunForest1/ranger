# Ranger

*[Read in English](./README.md)* · Лицензия: [Apache 2.0](./LICENSE)

Self-hosted CI/CD-хаб с метриками для одного сервера и 2–5 доверенных
пользователей. Добавляешь проект по SSH-ссылке на git-репозиторий, задаёшь три
команды — install, test, build — и нажимаешь «Собрать» (или ставишь cron). Дальше
в одной вкладке видно живой лог сборки, статус шагов, деплой в Docker-контейнер
и метрики контейнера и хоста.

Это лёгкая замена связке Jenkins + Portainer + кусок Grafana: один
`docker compose up`, никакого YAML-конфига пайплайнов и плагинов.

## Зачем я это делаю

У меня один домашний сервер и несколько своих проектов на нём. Поднимать ради них
три отдельных сервиса — CI, панель контейнеров и мониторинг — избыточно, а
деплоить руками через `ssh` + `git pull` + `docker build` надоело. Ranger
закрывает весь путь от коммита до работающего контейнера в одном инструменте.

Из этого три приоритета:

1. **Скорость настройки проекта важнее гибкости.** SSH-ссылка, deploy-key и три
   текстовых поля команд — это весь конфиг.
2. **Логи и метрики — треть продукта, а не довесок.** Сборка без живого лога и
   деплой без метрик контейнера — недоделанный инструмент.
3. **Безопасность проверяется в каждой итерации.** Сборки идут в изолированных
   контейнерах без привилегий, секреты шифруются, терминал — только для admin и
   только с повторным вводом пароля.

## Что умеет

- **Проекты и сборки** — install → test → build в изолированном контейнере с
  лимитами (512 МБ памяти, 1 CPU, ограничение числа процессов, таймаут 15 минут
  на шаг). Сборки одного проекта идут строго по очереди. Живой лог по WebSocket.
- **Деплой** — если в корне репозитория есть `Dockerfile` и в проекте заданы
  порты: сборка образа → остановка старого контейнера → запуск нового →
  health-check → автоматический откат на предыдущий образ при неудаче. Плюс
  ручной откат на любую прошлую успешную сборку.
- **Переменные окружения** — задаются в настройках проекта, попадают и в шаги
  сборки, и в задеплоенный контейнер. Хранятся зашифрованными, после сохранения
  не показываются, в логе сборки маскируются.
- **Ветки** — можно собрать любую ветку; деплоится только основная.
- **Триггеры** — вручную или по cron.
- **Контейнеры** — все контейнеры хоста, их статус и живые логи.
- **Метрики** — CPU/RAM/диск хоста и CPU/RAM каждого контейнера с графиком за час.
- **Файлы** — просмотр рабочей директории проекта (только чтение).
- **Терминал** — шелл в контейнере проекта или в его рабочей директории, только
  для admin, с повторным вводом пароля и записью в журнал аудита.
- **Пользователи и роли** — `admin`, `operator`, `viewer`, журнал аудита.
- **Публичная страница статуса** `/status` — только для проектов, где это явно
  включено: название, статус и время последней сборки.
- **Интерфейс** — светлая и тёмная тема, RU/EN, командная палитра `Ctrl+K`.

## Стек

| Слой | Выбор |
|---|---|
| Backend | NestJS, TypeScript, Prisma |
| База и очередь | PostgreSQL, pg-boss (очередь сборок в той же базе) |
| Docker | `dockerode` через сокет хоста |
| Изоляция сборок | [sandbox-executor](https://github.com/RunForest1/sandbox-executor) — отдельный пакет |
| Реалтайм | WebSocket (socket.io) |
| Frontend | React 18, Vite, Tailwind, Zustand, react-i18next |
| Пакеты и скрипты | Bun (прод-процесс backend работает на Node) |
| Хостинг | свой сервер, `docker compose` |

Модуль изоляции вынесен в отдельный репозиторий и ничего не знает о Ranger:
«образ + команда + лимиты → результат». Его же использует другой мой проект как
«судью» для задач по алгоритмам. Ranger подключает его git-зависимостью с тегом
версии (`#v0.2.0`).

```
CLAUDE.md                  архитектура, модель данных, правила разработки
```

## Установка на сервер

Нужен Linux-сервер с Docker и Docker Compose, доступом в интернет (для
`bun install` и образов) и правами на `docker` (root или группа `docker`).

### 1. Код и конфиг

```bash
git clone https://github.com/RunForest1/ranger.git
cd ranger
cp .env.example .env
```

Заполнить `.env`:

| Переменная | Что это |
|---|---|
| `SESSION_SECRET` | секрет cookie-сессий: `openssl rand -hex 32` |
| `DEPLOY_KEY_ENCRYPTION_KEY` | ключ шифрования deploy-key и переменных окружения: `openssl rand -hex 32`. **После первого сохранённого проекта не менять** — уже сохранённые секреты перестанут расшифровываться. Сохраните его вне сервера |
| `RANGER_WORKDIR_HOST_PATH` | абсолютный путь **на хосте** под чекауты сборок, например `/srv/ranger/build-workdir` |
| `ADMIN_EMAIL` | email первого администратора |

```bash
sudo mkdir -p /srv/ranger/build-workdir   # тот же путь, что в RANGER_WORKDIR_HOST_PATH
```

Почему путь на хосте: backend работает в контейнере, но управляет Docker через
сокет хоста. Когда он просит смонтировать чекаут в контейнер сборки, демон
резолвит путь относительно хоста, а не backend-контейнера.

### 2. Запуск

```bash
docker compose up -d --build
```

Что происходит при первом старте:

1. Собираются образы backend и frontend.
2. Поднимается PostgreSQL; backend ждёт, пока он станет доступен.
3. Backend применяет миграции (`prisma migrate deploy`).
4. Backend собирает образ `ranger-builder:latest`, в котором выполняются шаги
   сборки (Node 20, Bun, Python, build-essential). **Это занимает несколько
   минут**, пока не закончится — интерфейс отвечает 502. Следить:
   `docker compose logs -f backend`.
5. На пустой базе создаётся администратор с `ADMIN_EMAIL`, его пароль один раз
   печатается в лог.

Интерфейс — на порту `8080`. Пароль администратора:

```bash
docker compose logs backend | grep -A2 "первый администратор"
```

При первом входе пароль нужно сменить. Остальных пользователей администратор
заводит на странице «Пользователи» с ролью `admin`, `operator` или `viewer`.

Потеряли пароль:

```bash
docker compose exec backend node dist/cli/reset-password.js admin@example.com
```

Хаб отдаёт обычный HTTP. В локальной сети или за VPN этого достаточно; если
открывать его в интернет — поставьте перед ним reverse proxy с HTTPS.

### Обновление

```bash
git pull
docker compose up -d --build
```

Миграции применяются сами при старте backend. Данные (база, логи сборок, чекауты)
лежат в volume'ах и в `RANGER_WORKDIR_HOST_PATH` и переживают пересборку.

## Подключение первого проекта

### 1. Deploy-key

Ranger клонирует репозиторий по SSH отдельным ключом только на чтение — не вашим
личным ключом. Создайте его на любой машине:

```bash
ssh-keygen -t ed25519 -f ranger_deploy -N "" -C "ranger"
```

- `ranger_deploy.pub` — в репозиторий на GitHub: **Settings → Deploy keys → Add
  deploy key**, галочку **Allow write access не ставить**.
- `ranger_deploy` (приватный) — в форму проекта в Ranger. После этого файл можно
  удалить: в Ranger ключ хранится зашифрованным.

### 2. Проект в Ranger

**Добавить проект**:

- **Git URL** — SSH-ссылка: `git@github.com:owner/repo.git`.
- **Deploy-key** — содержимое `ranger_deploy`. Кнопка «Проверить репозиторий»
  сразу подтянет список веток — если он пришёл, доступ настроен верно.
- **Команды** — шаблоны npm/bun/python или свои. Нужна хотя бы одна. Команды
  выполняются в корне репозитория в образе `ranger-builder` с доступом в интернет
  (чтобы ставить пакеты).
- **Переменные окружения** — если сборке или приложению нужны токены и адреса.
  Можно вставить готовый `.env`.

### 3. Деплой (необязательно)

Чтобы Ranger не только собирал, но и запускал проект:

1. В корне репозитория должен лежать `Dockerfile`. Образ собирается из чекаута
   **после** шагов install/test/build, так что в нём уже есть результаты сборки
   (например, `dist/`).
2. В настройках проекта раскрыть «Деплой» и указать **порт контейнера** (который
   слушает приложение внутри) и **порт хоста** (на котором оно будет доступно
   снаружи).

Health-check проверяет, что порт контейнера начал принимать TCP-соединения за
30 секунд. Если нет — Ranger возвращает предыдущий рабочий образ.

Задеплоенный контейнер называется `ranger-deploy-<id проекта>`, перезапускается
сам (`unless-stopped`) и переживает перезагрузку сервера.

## Безопасность

- Docker-сокет есть только у backend — в контейнеры сборки и деплоя он не
  пробрасывается.
- Шаги сборки: без `--privileged`, все capabilities сброшены, `no-new-privileges`,
  лимиты памяти/CPU/процессов, принудительный таймаут.
- Deploy-key и переменные окружения шифруются на уровне приложения (AES-256-GCM)
  и не попадают в API-ответы. Расшифровать их может только admin, и каждый такой
  запрос пишется в журнал аудита.
- Терминал — только admin, повторный ввод пароля, запись в журнал, лимит сессии.
- Пароли хранятся как хэши `argon2`. Регистрации нет: пользователей заводит admin.

> Docker-сокет даёт root-доступ к хосту. Тот, кто может изменить код backend или
> получить в нём выполнение команд, контролирует сервер. Ranger рассчитан на
> доверенных пользователей (роль `operator` уже означает «может запускать
> произвольные команды сборки в контейнере с доступом в интернет»), а не на
> публичное использование.

## Локальная разработка

```bash
cp .env.example .env
cp apps/backend/.env.example apps/backend/.env
docker compose up -d postgres

bun install                  # заодно подтянет sandbox-executor с GitHub

cd apps/backend
bunx prisma migrate dev      # применит миграции
bun run dev                  # http://localhost:3000, на пустой базе напечатает пароль admin'а

cd ../frontend
bun run dev                  # http://localhost:5173, проксирует /api и /socket.io на backend
```

Проверки (их же гоняет CI в `.github/workflows/ci.yml`):

```bash
bun run lint                 # backend + frontend
bun run build                # backend + frontend
```

Нужен доступ к Docker-сокету (пользователь в группе `docker`): backend запускает
контейнеры сборки. Схема базы меняется через `bunx prisma migrate dev --name <имя>`;
получившуюся миграцию нужно закоммитить, в проде применяется только
`prisma migrate deploy`.

# Документация

## Как устроена сборка

Жизненный цикл одной сборки:

1. **Запуск.** Кнопка «Собрать», cron или API создают запись `builds` со статусом
   `queued` и кладут задание в очередь проекта. Ветка выбирается при запуске; по
   умолчанию — основная ветка проекта.
2. **Очередь.** Для каждого проекта своя очередь pg-boss, задания в ней идут строго
   по одному: сборки одного проекта не выполняются параллельно, разных проектов —
   могут. Очередь хранится в PostgreSQL и переживает перезапуск.
3. **Клонирование.** Backend расшифровывает deploy-key, кладёт его во временный
   файл (права `600`) и клонирует нужную ветку системным `git` в новую директорию
   `repo-*` внутри `RANGER_WORKDIR_HOST_PATH`. Временный ключ удаляется сразу после.
4. **Шаги `install` → `test` → `build`.** Каждый непустой шаг — отдельный запуск
   контейнера `ranger-builder:latest` с монтированием чекаута в `/workspace`.
   Пустые шаги пропускаются. Первый упавший шаг останавливает сборку, остальные
   получают статус `skipped`. Вывод стримится в лог и по WebSocket.
5. **Шаг `deploy`** добавляется, только если у проекта заданы оба порта **и**
   собирается основная ветка. Сборка любой другой ветки проходит install/test/build,
   но работающую версию не подменяет.
6. **Завершение.** Чекаут переносится в `projects/<id>` (одна копия на проект,
   предыдущая заменяется) — из неё работают файловый браузер и терминал в рабочей
   директории. Сборка получает статус `success` или `failed`.

Если backend был перезапущен во время сборки, при старте она помечается `failed`
с пояснением в логе, а незавершённые чекауты удаляются.

**Что считается неудачей:** ненулевой код выхода шага, таймаут (15 минут на шаг —
контейнер убивается `SIGKILL`), падение клонирования (неверный URL, нет доступа) или
ошибка деплоя. Причина всегда видна в логе сборки в интерфейсе.

### Шаги и образ сборки

Шаги выполняются командой `sh -c "<ваша команда>"` в образе `ranger-builder:latest`
(`apps/backend/docker/builder.Dockerfile`): Node 20, Bun, Python 3 + pip,
build-essential, curl, unzip. Если проекту нужно что-то ещё, поставьте это в
`install` (сеть в шагах сборки включена) или расширьте образ и пересоберите его:

```bash
docker rmi ranger-builder:latest
docker compose restart backend      # backend соберёт образ заново при старте
```

Внутри контейнера: рабочая директория `/workspace` (чекаут, запись разрешена),
лимит 512 МБ памяти, 1 CPU, 256 процессов, все capabilities сброшены,
`no-new-privileges`, Docker-сокета нет.

## Деплой

Если в проекте заданы порт контейнера и порт хоста, после успешных шагов сборки:

1. Проверяется наличие `Dockerfile` в корне чекаута; иначе деплой падает с
   понятным сообщением.
2. Из чекаута собирается образ `ranger-deploy-<id проекта>:<id сборки>`.
   Если сборка образа упала — старый контейнер не трогается.
3. Останавливается и удаляется предыдущий контейнер проекта.
4. Создаётся новый контейнер `ranger-deploy-<id проекта>`: порт контейнера
   публикуется на порт хоста, переменные окружения проекта передаются в `Env`,
   политика перезапуска `unless-stopped`. Контейнер подключается к тем же
   docker-сетям, что и backend (так health-check достукивается до него по имени).
5. **Health-check:** TCP-подключение к порту контейнера, до 30 секунд с опросом раз в
   секунду. Проверяется только то, что порт слушает, а не HTTP-ответ.
6. При неудаче Ranger останавливает новый контейнер и запускает образ последнего
   успешного деплоя (автооткат). Если откатываться не на что — контейнера просто нет.

Каждая попытка записывается в историю деплоев. **Ручной откат** — кнопка у любой
записи со статусом «успешно»: образ уже лежит в Docker, поэтому пересборки нет,
контейнер просто переключается на него и проходит тот же health-check.

Старые образы не удаляются автоматически (они нужны для отката). Если место на диске
кончается: `docker image prune` или удаление ненужных `ranger-deploy-*` вручную.

При удалении проекта его контейнер останавливается и удаляется.

## Переменные окружения проекта

Настройки проекта → «Переменные окружения». Значения попадают:

- в **каждый шаг сборки** (`install`, `test`, `build`) как обычные переменные
  процесса;
- в **задеплоенный контейнер** (при деплое, автооткате и ручном откате).

Правила:

- Имя — латиница, цифры и `_`, не с цифры. До 200 переменных на проект.
- Значения хранятся зашифрованными, после сохранения интерфейс их **не показывает**:
  у сохранённой переменной поле значения пустое, пустое = «не менять». Изменить
  значение — ввести новое; удалить — крестик.
- Можно вставить содержимое готового `.env` (`KEY=value`, комментарии `#`,
  необязательный `export`, значения в кавычках). Многострочные значения не
  поддерживаются.
- Admin может посмотреть значения кнопкой «Показать значения» — это пишется в журнал
  аудита (`reveal_project_env`).
- Изменения применяются **со следующей сборки или деплоя**. Запущенный контейнер при
  сохранении не перезапускается.
- Значения длиной от 8 символов маскируются (`***`) в логе сборки. Более короткие
  (`PORT=3000`, `DEBUG=true`) не маскируются, чтобы не портить лог. Маскировка
  работает только для лога сборки: если приложение само печатает секреты в свой
  stdout, они будут видны в логах контейнера.
- При откате используются **текущие** переменные проекта, а не те, с которыми образ
  деплоился раньше: прежние значения не хранятся.

## Метрики

- **Хост:** CPU, RAM, диск. Читаются из `/proc` (в контейнере они отражают хост) и с
  диска, где лежат чекауты сборок.
- **Контейнеры:** CPU и RAM каждого запущенного контейнера через Docker API
  (`stats`), не Prometheus.
- Замер каждые 5 секунд, живое обновление по WebSocket, график за последний час.
- История хранится **в памяти backend** и теряется при его перезапуске. Долгосрочных
  метрик нет: для этого нужен Prometheus/Grafana, и Ranger их не заменяет.

## Терминал

Вкладка «Консоль» проекта, только для роли `admin`. Это не шелл хоста: доступно
два варианта.

- **Шелл в контейнере проекта** — `exec` в задеплоенный контейнер проекта (нужно,
  чтобы проект был задеплоен и контейнер запущен).
- **Шелл в рабочей директории** — одноразовый контейнер `ranger-builder` над
  последним чекаутом, `/workspace`. Без сети, 512 МБ, 1 CPU, 256 процессов.

Порядок и ограничения:

1. Перед первым входом (и раз в 5 минут) запрашивается пароль — отдельное
   подтверждение поверх обычной сессии.
2. Попытка входа пишется в журнал аудита (`open_terminal`) **до** запуска шелла.
3. Сессия ограничена 30 минутами независимо от активности; при закрытии вкладки
   контейнер терминала удаляется.

## Файлы

Вкладка «Файлы» проекта — просмотр последнего чекаута, только чтение. Доступны все
роли. Ограничения: текстовые файлы до 1 МБ (бинарные и крупные показываются как
«нельзя открыть»); выход за пределы чекаута, в том числе через симлинк в
репозитории, блокируется. Чекаут появляется после первой сборки.

## Триггеры и cron

У проекта два режима запуска: `manual` и `cron`. В режиме cron указывается обычное
пятиполевое выражение (`*/30 * * * *`, `0 3 * * *`). Расписание работает в часовом
поясе процесса backend (по умолчанию UTC). Cron всегда собирает основную ветку.
Такие сборки не пишутся в журнал аудита — «пользователя» у них нет, в поле
«запустил» стоит `cron`.

## Роли

| Возможность | viewer | operator | admin |
|---|:-:|:-:|:-:|
| Просмотр проектов, сборок, логов, деплоев, контейнеров, метрик, файлов | ✓ | ✓ | ✓ |
| Запуск сборки | | ✓ | ✓ |
| Создание, изменение и удаление проектов | | ✓ | ✓ |
| Замена deploy-key, изменение переменных окружения | | ✓ | ✓ |
| Откат деплоя | | ✓ | ✓ |
| Просмотр расшифрованного deploy-key и значений переменных | | | ✓ |
| Терминал | | | ✓ |
| Управление пользователями | | | ✓ |
| Журнал аудита | | | ✓ |

Права проверяются на сервере при каждом запросе, роль читается из базы: смена роли
или отключение пользователя действует сразу, без перелогина. Пользователя нельзя
удалить (записи аудита ссылаются на него) — только отключить. Себя нельзя отключить
или понизить, чтобы не остаться без администратора.

Пользователь с временным паролем (новый, сброшенный, первый admin) может только
сменить пароль, остальное API и WebSocket ему закрыты.

## Журнал аудита

Виден только admin, вкладка «Журнал аудита». Записываются: запуск сборки
пользователем, откат деплоя, просмотр deploy-key, просмотр переменных окружения,
вход в терминал, создание и изменение пользователя, сброс пароля. У каждой записи —
кто, что, над чем и когда.

## Публичная страница статуса

`/status` доступна без входа. Показывает только проекты, у которых включена галочка
«Показывать на публичной странице статуса»: название, статус последней сборки и её
время. Логов, URL репозитория и веток там нет. По умолчанию проект не публичный.

## Конфигурация

Переменные в корневом `.env` (их читает `docker-compose.yml`):

| Переменная | Обязательна | Описание |
|---|:-:|---|
| `SESSION_SECRET` | да | Секрет подписи cookie-сессий |
| `DEPLOY_KEY_ENCRYPTION_KEY` | да | Ключ шифрования deploy-key и переменных окружения. Не менять после первого сохранённого секрета |
| `RANGER_WORKDIR_HOST_PATH` | да | Абсолютный путь на хосте под чекауты сборок |
| `ADMIN_EMAIL` | при первом старте | Email первого администратора |

Переменные, которые compose передаёт в backend (при запуске без compose задаются
в `apps/backend/.env`):

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATABASE_URL` | — | Строка подключения к PostgreSQL |
| `PORT` | `3000` | Порт backend |
| `BUILD_WORKDIR_HOST_PATH` | — | Путь чекаутов на хосте (в compose = `RANGER_WORKDIR_HOST_PATH`) |
| `BUILD_WORKDIR_CONTAINER_PATH` | `/data/build-workdir` | Тот же каталог, как его видит backend |
| `BUILD_LOGS_DIR` | `data/build-logs` | Каталог логов сборок |

Значения, зашитые в код (`apps/backend/src`), меняются пересборкой:

| Что | Значение | Где |
|---|---|---|
| Таймаут шага сборки | 15 мин | `builds/build-runner.service.ts` |
| Память / CPU шага сборки | 512 МБ / 1 | `builds/build-runner.service.ts` |
| Таймаут health-check | 30 с | `deployments/deploy-runner.service.ts` |
| Повторный ввод пароля для терминала | 5 мин | `terminal/terminal.gateway.ts` |
| Максимум сессии терминала | 30 мин | `terminal/terminal.gateway.ts` |
| Интервал метрик, история | 5 с, 1 час | `metrics/` |

## Хранение данных и резервные копии

| Что | Где |
|---|---|
| Проекты, сборки, пользователи, аудит, очередь, сессии | PostgreSQL, volume `postgres-data` |
| Логи сборок (`<id сборки>.log`) | volume `build-logs` |
| Чекауты сборок и последний чекаут проекта | `RANGER_WORKDIR_HOST_PATH` на хосте |
| Образы задеплоенных приложений | Docker хоста (`ranger-deploy-*`) |

Для резервной копии достаточно **базы и `DEPLOY_KEY_ENCRYPTION_KEY`**. Без ключа
шифрования сохранённые deploy-key и переменные окружения не расшифровать, даже имея
копию базы. Остальное восстанавливается: чекауты появятся при следующей сборке.

```bash
docker compose exec postgres pg_dump -U ranger ranger > ranger-backup.sql
```

## Справочник API

Все пути с префиксом `/api`. Аутентификация — cookie-сессия (`POST /auth/login`).
Формат — JSON. Ошибки приходят как `{ "message": "..." }` с HTTP-кодом.

**Аутентификация**

| Метод и путь | Роль | Описание |
|---|---|---|
| `POST /auth/login` | — | `{ email, password }` → пользователь, cookie |
| `POST /auth/logout` | — | Завершает сессию |
| `GET /auth/me` | любая | Текущий пользователь |
| `POST /auth/change-password` | любая | `{ currentPassword, newPassword }` |
| `POST /auth/reauth` | admin | `{ password }` — подтверждение для терминала |

**Проекты**

| Метод и путь | Роль | Описание |
|---|---|---|
| `GET /projects`, `GET /projects/:id` | любая | Список / карточка (без секретов; `envKeys` — только имена) |
| `POST /projects` | operator | Создать проект (можно с `env`) |
| `PATCH /projects/:id` | operator | Изменить настройки |
| `DELETE /projects/:id` | operator | Удалить проект и его контейнер |

| `PUT /projects/:id/env` | operator | `{ variables: [{ key, value? }] }` — полный список |

**Сборки и деплои**

|---|---|---|

## WebSocket

Тот же адрес, `socket.io`, авторизация по той же сессии (подключение без входа или
с обязательной сменой пароля отклоняется).

| Namespace | Клиент → сервер | Сервер → клиент |
|---|---|---|
| `/` (сборки) | `subscribe` (id сборки) | `log` (строка), `steps` (шаги), `status` |
| `/containers` | `subscribe` (id контейнера), `unsubscribe` | `log` (строка; сначала последние 200) |
| `/metrics` | — | `host`, `container` (раз в 5 с, всем подключённым) |
| `/terminal` | `start` (`{ projectId, target }`), `input`, `resize`, `stop` | вывод шелла, коды ошибок и причины закрытия |

## Решение проблем

**Интерфейс отвечает 502 после запуска.** Backend ещё собирает образ
`ranger-builder` (на первом старте несколько минут). Следите за
`docker compose logs -f backend`.

**Backend падает: «BUILD_WORKDIR_HOST_PATH не задан».** В `.env` нет
`RANGER_WORKDIR_HOST_PATH`, либо путь не абсолютный.

**Сборка: `Permission denied (publickey)` при клонировании.** Публичная часть
deploy-key не добавлена в репозиторий, либо в Ranger вставлен не тот приватный ключ.
Проверьте кнопкой «Проверить репозиторий».

**Сборка падает, файлы не найдены / пустой `/workspace`.** Путь
`RANGER_WORKDIR_HOST_PATH` должен быть один и тот же на хосте и в volume backend.
Не меняйте его на работающей системе без пересоздания контейнера.

**Деплой: «в корне репозитория нет Dockerfile».** Деплой собирает образ из
`Dockerfile` в корне. Либо добавьте его, либо уберите порты в настройках проекта.

**Деплой: health-check не прошёл.** Приложение не начало слушать порт контейнера за
30 секунд, либо указан не тот порт. Смотрите логи контейнера на вкладке «Контейнеры».

**Деплой: порт хоста занят.** На этом порту уже что-то слушает — выберите другой.

**Забыли пароль администратора.**
`docker compose exec backend node dist/cli/reset-password.js <email>`.

**Сохранённые ключи и переменные не расшифровываются.** Изменился
`DEPLOY_KEY_ENCRYPTION_KEY`. Верните прежнее значение; если оно утеряно, ключи и
переменные придётся ввести заново.

## Ограничения и планы

- **Один хост.** Никакой оркестрации, кластеров и нескольких серверов.
- **Ошибки API только на русском.** Backend отдаёт готовый русский текст, поэтому
  в EN-режиме сообщения об ошибках не переводятся. Правильнее отдавать коды ошибок
  и переводить их на фронтенде — так уже сделано для терминала.
- **Лимиты для задеплоенных контейнеров.** Шаги сборки ограничены, а контейнеры
  `ranger-deploy-*` пока запускаются без лимитов CPU и памяти.
- **Health-check — только TCP.** HTTP-проверка пути не поддерживается.
- **Метрики только за час** и не переживают перезапуск.
- **Уведомлений нет** (Telegram и другие не планируются).
